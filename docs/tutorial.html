feedlab

feedlab est un petit feed handler de market data (format Binance bookTicker) accompagné d'une stratégie de test qui ne demande presque jamais d'écrire des données de test à la main.

Généré par tools/build_tutorial.py à partir des fichiers réels du projet : aucun chiffre n'est saisi à la main.

Le handler

#1. Le projet en une phrase

feedlab est un petit feed handler de market data, et surtout une stratégie pour le tester sans écrire les données de test à la main.

feedlab est un petit feed handler de market data (format Binance bookTicker) accompagné d'une stratégie de test qui ne demande presque jamais d'écrire des données de test à la main.

Le schéma ci-dessous montre la chaîne complète. Cliquez sur un bloc (ou utilisez Tab puis Entrée) pour ouvrir son explication.

Aucun bloc sélectionné.

Enregistrement recordings/session_calm.jsonl

Une ligne JSON par message, au format Binance bookTicker, avec l'heure de réception recv_ts_ns. Les deux sessions (5000 et 20000 messages) sont produites par testdata/generate_session.py avec une graine : même graine, même fichier à l'octet près.

Rejeu feedlab/replay.py

Le rejeu lit la session et injecte chaque ligne dans le handler, soit au rythme d'origine (--speed 1), soit accéléré (--speed N), soit le plus vite possible (--speed 0).

Parser feedlab/parser.py

Le parser transforme une ligne en message, ou en raison de rejet. Il ne lève jamais d'exception. Les prix sont des Decimal, jamais des float. S'il peut lire le symbole et u, il les rend même pour un message rejeté.

Carnet feedlab/book.py

Le carnet garde le meilleur prix (top of book) par symbole. Il refuse un carnet croisé (bid ≥ ask) et n'accepte jamais une cotation plus ancienne que celle qu'il a.

Sortie abonné feedlab/dump.py

Une ligne clé=valeur par événement (QUOTE, GAP, SKIP, DUPLICATE, REJECT), terminée par trois champs qui changent à chaque exécution : proc_ts, host, latency_ns.

Caviardage feedlab/redact.py

Remplace proc_ts (exactement 19 chiffres), host et latency_ns par des jetons fixes. Rien d'autre.

Comparaison scripts/compare.sh

La sortie caviardée est comparée à un corrigé (scripts/compare.sh) ou à la sortie d'une autre version (tools/differential.py). Code retour 0 si identique, 1 sinon.

#2. Le parcours d'un message

Un message traverse six étapes, et à chaque étape une seule chose change.

On suit un vrai message de l'échantillon, celui qui révèle un trou de séquence. Chaque étape montre ce que fait un module, avec les valeurs réelles.

  1. Étape 1 Enregistrement samples/sample.jsonl

    On prend la ligne 5 de samples/sample.jsonl. C'est une ligne JSON brute, telle qu'elle a été « reçue ».

    {"recv_ts_ns":1700000030000400000,"raw":{"stream":"btcusdt@bookTicker","data":{"u":104,"s":"BTCUSDT","b":"67000.30","B":"0.4","a":"67000.40","A":"0.9"}}}

  2. Étape 2 Rejeu feedlab/replay.py

    Le rejeu lit recv_ts_ns = 1700000030000400000. Le message précédent a été reçu 100 µs plus tôt : à --speed 1, le rejeu attend 100 µs ; à --speed 0, il n'attend pas. Puis il injecte la ligne dans le handler.

  3. Étape 3 Parser feedlab/parser.py

    Le parser lit le JSON, vérifie chaque champ et convertit les prix en Decimal. Aucun champ ne pose problème, donc pas de raison de rejet.

    ChampValeur lue
    symboleBTCUSDT
    u104
    bid (b)Decimal('67000.30')
    bid_qty (B)Decimal('0.4')
    ask (a)Decimal('67000.40')
    ask_qty (A)Decimal('0.9')
    raison de rejetaucune

  4. Étape 4 Règles de séquence feedlab/handler.py

    Pour BTCUSDT, le dernier numéro consommé est 102. Le message porte u = 104, plus grand que 102 + 1 : le handler émet d'abord un GAP (attendu 103, reçu 104), puis accepte le message. Le dernier numéro devient 104.

  5. Étape 5 Carnet feedlab/book.py

    Le carnet vérifie bid < ask (67000.30 < 67000.40) : ce n'est pas croisé. Il remplace le top of book.

    ubidask
    avant10267000.1567000.20
    après10467000.3067000.40

  6. Étape 6 Sortie abonné feedlab/dump.py

    Deux lignes sont émises : le GAP, puis la QUOTE. Les trois derniers champs changent à chaque exécution (valeurs réelles, mesurées lors de la génération de ce tutoriel).

    GAP sym=BTCUSDT expected=103 received=104 proc_ts=1794417324776607209 host=debian latency_ns=4583
QUOTE sym=BTCUSDT u=104 bid=67000.30 bid_qty=0.4 ask=67000.40 ask_qty=0.9 proc_ts=1794417324776607543 host=debian latency_ns=4916

  7. Étape 7 Caviardage feedlab/redact.py

    Le caviardage remplace proc_ts, host et latency_ns par des jetons fixes. Le symbole, les numéros et les prix restent intacts.

    GAP sym=BTCUSDT expected=103 received=104 proc_ts=<TS> host=<HOST> latency_ns=<LAT>
QUOTE sym=BTCUSDT u=104 bid=67000.30 bid_qty=0.4 ask=67000.40 ask_qty=0.9 proc_ts=<TS> host=<HOST> latency_ns=<LAT>

  8. Étape 8 Comparaison samples/expected_output.txt

    Les lignes 5 et 6 du corrigé samples/expected_output.txt sont identiques : le test test_sample_matches_expected_output passe pour ce message.

    GAP sym=BTCUSDT expected=103 received=104 proc_ts=<TS> host=<HOST> latency_ns=<LAT>
QUOTE sym=BTCUSDT u=104 bid=67000.30 bid_qty=0.4 ask=67000.40 ask_qty=0.9 proc_ts=<TS> host=<HOST> latency_ns=<LAT>

#4. Le caviardage

On masque uniquement ce qui change à chaque exécution, et rien d'autre.

Ce qui est masquéRemplacé parPourquoi
proc_ts= + exactement 19 chiffresproc_ts=<TS>Horodatage en nanosecondes : change à chaque exécution.
host=…host=<HOST>Nom de la machine : change d'une machine à l'autre.
latency_ns=…latency_ns=<LAT>Mesure de temps : change à chaque message.
Ce qui n'est jamais masquéPourquoi
Prix et quantités (bid, ask, bid_qty, ask_qty)C'est ce qu'on veut vérifier. Les masquer donnerait un test qui passe toujours.
Symbole (sym)Une erreur de routage doit se voir.
Numéros de séquence (u, expected, received, last)Les règles de séquence sont le cœur du handler.
Un proc_ts à 18 ou 20 chiffresCe n'est plus un horodatage valide : c'est un bug, il doit faire échouer la comparaison.

Les données de test
#7. Les mutations
Une mutation abîme une session de façon contrôlée, et annonce à l'avance l'effet exact sur les compteurs.


Les 14 opérateurs ci-dessous ont été appliqués à recordings/session_calm.jsonl avec la graine 1 au moment de générer ce tutoriel. La colonne « Événements » est la sortie réelle du handler pour chaque ligne. Les lignes surlignées sont la cible ou les lignes modifiées.


Effet en chaîne : un message retardé crée un GAP à l'arrivée du suivant, puis un SKIP à sa propre arrivée.
Pas de faux GAP : un message rejeté dont le u est lisible consomme son numéro.
Contre-exemple : sans u lisible, rien n'est consommé et le GAP suivant est légitime.

#13. Limites et simplifications
Ce que le projet ne fait pas est écrit noir sur blanc, pour pouvoir en parler honnêtement.
  • Numéros de séquence contigus par symbole. C'est une simplification : chez Binance, u est un identifiant de mise à jour du carnet, pas un compteur contigu par flux.
  • Enregistrements simulés. recordings/ est produit par un générateur (marche aléatoire, rafales, quelques anomalies naturelles). Ce ne sont pas de vraies captures : les microstructures réelles (rafales corrélées entre symboles, reconnexions, messages de carnet profond) n'y sont pas.
  • Top of book seulement. Pas de profondeur de carnet, pas de snapshot ni de resynchronisation par snapshot : après un GAP, on accepte simplement le message.
  • Champ stream non vérifié. Sa cohérence avec s n'est pas contrôlée.
  • Parser strict. Les nombres doivent être des chaînes au format décimal canonique : 1e5, 01.5, +1, NaN et les nombres JSON (qui passeraient par un float) sont rejetés. Une quantité 0 est acceptée.
  • Latence mesurée en Python, dans un seul processus, sans réseau ni noyau : ce sont des microsecondes Python, pas celles d'un handler C++ en kernel bypass.
  • Bruit de la VM. Sur la machine virtuelle de développement, le p99 en temps réel varie de +16 % à +115 % d'une série à l'autre sans aucun changement de code (préemption par l'hyperviseur). Le scénario realtime bloque donc sur le p50, qui reste stable ; son p99 est affiché pour information. Le scénario burst bloque bien sur le p99.
  • Opérateurs de mutation. Ils ne visent qu'un message dans un « voisinage propre » (message en séquence, suivants contigus et valides), pour que le delta reste une formule exacte. truncate_last refuse une session dont la dernière ligne n'est pas une cotation en séquence. Le contrôle de validité de testdata/mutate.py reprend volontairement, en plus simple, les règles du parser.
  • Hypothesis en mode derandomize=True. Les mêmes exemples reviennent à chaque exécution, ce qui garantit la reproductibilité mais explore moins qu'un mode aléatoire.
  • Différentiel. La version de référence doit déjà contenir la commande python -m feedlab.dump (c'est le cas depuis le premier commit). Les sessions rejouées sont celles de l'arbre courant.
  • Robot ne lit aucun fichier de configuration. L'exclusion de la latence par défaut passe donc par un Skip If.
  • Hors périmètre : CI, Jenkins, exécutions planifiées.
